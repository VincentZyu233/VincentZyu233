# 在 iPad 的 iSH 中安装 Node.js 并尝试运行 Koishi

iSH 可以在 iPadOS 上运行一个基于 Alpine Linux 的用户态环境。本文记录如何为 iSH 更换中科大软件源、启用局域网 SSH、安装 Fastfetch 与 Node.js，并创建一个 Koishi 模板项目。

> iSH 通过 x86 用户态模拟运行 Linux 程序，性能和兼容性都不能等同于原生 Linux。Koishi 本体可以尝试运行，但依赖安装、原生模块编译和长期后台运行都可能受到限制。重要项目应部署在服务器、NAS 或其他原生 Node.js 环境中。

## 🔹 临时保持 iPad 屏幕常亮

安装 npm 依赖或运行 Koishi 时，应先避免 iPad 自动锁屏。iSH 进入后台后会被 iPadOS 挂起，内存紧张时还可能被系统终止，回到应用后就可能发现终端进程已经消失。

最直接的方法：

1. 打开“设置 → 显示与亮度 → 自动锁定”。
2. 临时选择“永不”。
3. 操作结束后恢复原来的自动锁定时间，避免持续耗电和屏幕长时间显示静止内容。

如果只想在使用 iSH 时保持屏幕常亮，可以使用引导式访问：

1. 打开“设置 → 辅助功能 → 引导式访问”，启用该功能。
2. 在引导式访问设置中，将“显示屏自动锁定”设为“永不”。
3. 打开 iSH，连按三次顶部按钮；带 Home 键的机型则连按三次 Home 键。
4. 选择“引导式访问”并开始。
5. 使用结束后再次连按三次相同按钮，验证密码或 Face ID，然后结束引导式访问。

上述路径适用于 iPadOS 26，也适用于菜单结构相近的 iPadOS 27。可以在“设置 → 通用 → 关于本机 → iPadOS 版本”查看当前确切版本；测试版或受设备管理策略控制的系统，选项名称和可用范围可能略有不同。

长时间安装时建议接入电源并降低亮度。屏幕常亮只能降低 iSH 被挂起的概率，无法阻止 iPadOS 在内存不足时终止应用；`tmux` 也只能保留仍在运行的终端会话，不能挽救已经被系统终止的 iSH 进程。

## 🔹 开始之前

先确认 iPad 和准备连接它的电脑位于同一个 WLAN。本文示例使用以下地址和端口：

- iPad 地址：`192.168.31.163`
- SSH 端口：`2222`
- Koishi 控制台端口：`5140`

iPad 的地址可能由 DHCP 自动变化，应以“设置 → WLAN → 当前网络”中显示的地址为准。

在 iSH 中查看系统版本和架构：

```bash
cat /etc/alpine-release
uname -m
```

iSH 通常显示为 `x86` 或 `i686`。后续软件是否可安装，取决于当前 Alpine 版本的软件仓库是否仍为该架构提供对应软件包。

## 🔹 更换中科大 Alpine 镜像

本文使用的 iSH 文件系统是 Alpine 3.14.3，默认仓库不是标准的 `dl-cdn.alpinelinux.org`，而是 iSH 固定快照：

```text
http://apk.ish.app/v3.14-2023-05-19/main
http://apk.ish.app/v3.14-2023-05-19/community
```

因此，替换 `dl-cdn.alpinelinux.org` 的通用命令不会修改任何内容。先备份当前仓库配置：

```bash
cp -p /etc/apk/repositories /etc/apk/repositories.ish.bak
```

将 iSH 的 Alpine 3.14 固定快照路径替换为 USTC 的标准 Alpine 3.14 路径：

```bash
sed -i 's|http://apk\.ish\.app/v3\.14-2023-05-19|https://mirrors.ustc.edu.cn/alpine/v3.14|g' /etc/apk/repositories
cat /etc/apk/repositories
apk update
```

修改后应显示：

```text
https://mirrors.ustc.edu.cn/alpine/v3.14/main
https://mirrors.ustc.edu.cn/alpine/v3.14/community
```

本次实测 `apk update` 成功读取了 USTC 的 Alpine 3.14 x86 索引。如果需要恢复 iSH 固定快照：

```bash
cp -p /etc/apk/repositories.ish.bak /etc/apk/repositories
apk update
```

`/etc/apk/repositories` 的文件头说明该文件由 iSH 管理。只要 `/ish` 目录存在，iSH 就可能在启动时根据 `/ish/apk-version` 重新生成仓库配置；重启后如果源被还原，需要重新执行上述替换命令。

Alpine 3.14 已停止支持。不要为了安装新版 Node.js 就把仓库直接改成 `v3.23`、`edge` 或 `latest-stable`，否则会在旧文件系统中混装跨版本软件包。USTC 对不再收录的旧版本也可能重定向回官方源。

中科大镜像帮助页面：<https://mirrors.ustc.edu.cn/help/alpine.html>

## 🔹 开启 SSH 并允许局域网连接

iOS 应用通常不能监听 `22` 这类特权端口，因此这里让 SSH 服务监听 `2222`。

安装 OpenSSH 并生成服务器密钥：

```bash
apk add openssh openssh-server nano
ssh-keygen -A
mkdir -p /run/sshd
```

不建议开放 root 密码登录。创建一个普通用户，并按照提示设置密码：

```bash
adduser koishi
```

> **可选：开启 root 密码 SSH 登录**
>
> 只建议在可信局域网中临时使用，不要把 SSH 端口映射到公网。先为 root 设置一个强且不与其他服务重复的密码：
>
> ```bash
> passwd
> ```
>
> 编辑 OpenSSH 服务端配置：
>
> ```bash
> nano /etc/ssh/sshd_config
> ```
>
> 找到并修改以下配置；如果原行以 `#` 开头，需要去掉 `#`。这两行应放在任何 `Match` 段之前：
>
> ```text
> PermitRootLogin yes
> PasswordAuthentication yes
> ```
>
> 保存配置后，继续执行下方的 `sshd -t` 和启动命令。然后可从电脑连接：
>
> ```bash
> ssh -p 2222 root@192.168.31.163
> ```
>
> 不再需要 root 登录时，将 `PermitRootLogin` 改回 `no`。如果 SSH 服务已经启动，修改配置后执行 `pkill sshd`，再按下方命令检查配置并重新启动。

检查 SSH 配置是否有效，然后启动服务：

```bash
/usr/sbin/sshd -t
/usr/sbin/sshd -p 2222
```

确认服务监听在所有网络接口，而不只是 `127.0.0.1`：

```bash
netstat -lnt | grep 2222
```

正常情况下会看到 `0.0.0.0:2222` 或 `:::2222`。随后在同一局域网的电脑上连接：

```bash
ssh -p 2222 koishi@192.168.31.163
```

Windows PowerShell 也可以使用相同的 `ssh` 命令。首次连接会询问是否信任主机密钥，确认地址无误后输入 `yes`，再输入刚才设置的用户密码。

连接失败时，可以在 Windows 上检查端口：

```powershell
Test-NetConnection 192.168.31.163 -Port 2222
```

还应检查以下事项：

- 在 iPad 的“设置 → 隐私与安全性 → 本地网络”中允许 iSH 访问本地网络。
- 两台设备连接同一个 WLAN，路由器没有启用 AP 隔离或客户端隔离。
- iPad 地址没有发生变化。
- 保持 iSH 位于前台。iPadOS 挂起 iSH 后，SSH 连接也会中断。

需要观察 SSH 服务端错误时，可以先停止服务，再以前台调试模式运行：

```bash
pkill sshd
/usr/sbin/sshd -D -e -p 2222
```

按 `Ctrl+C` 退出调试模式，之后可重新以普通方式启动。

## 🔹 安装 Fastfetch

Alpine 3.14 的 main 和 community 仓库没有 Fastfetch。下面的查询不会返回软件包：

```bash
apk search -x fastfetch
```

直接安装会得到 `fastfetch (no such package)`，不要为此混入 `edge` 或其他 Alpine 版本的仓库：

```bash
apk add fastfetch
```

### 尝试官方 i686 二进制

Fastfetch 2.67.1 的 GitHub Release 提供 `fastfetch-linux-i686.tar.gz`，架构与 iSH 一致。网络直连失败时，可以临时使用局域网代理：

```bash
export http_proxy=http://192.168.31.233:7890
export https_proxy=http://192.168.31.233:7890
```

下载并检查官方包：

```bash
apk add wget tar gcompat file
mkdir -p /tmp/fastfetch-release
cd /tmp/fastfetch-release
wget https://github.com/fastfetch-cli/fastfetch/releases/download/2.67.1/fastfetch-linux-i686.tar.gz
tar -xzf fastfetch-linux-i686.tar.gz
file fastfetch-linux-i686/usr/bin/fastfetch
ldd fastfetch-linux-i686/usr/bin/fastfetch
```

该二进制使用 `/lib/ld-linux.so.2` 和 glibc ABI。即使安装 Alpine 3.14 的 `gcompat 1.0.0`，实测仍缺少 `__fstat64_time64`、`__nanosleep64`、`__printf_chk` 等符号，不能在当前 iSH 中运行。因此不要把这个二进制复制到系统目录，改为使用下面的 musl 原生编译方案。

检查完成后可删除临时下载：

```bash
rm -rf /tmp/fastfetch-release
```

### 从源码编译兼容版本

Fastfetch 2.67.1 已要求 GCC 13 和 C23，而 Alpine 3.14 只有 GCC 10.3 与 CMake 3.20。最后一个仍使用 C11、可在该环境构建的正式版本是 2.66.0。

安装 Git 和构建依赖：

```bash
apk add git build-base cmake linux-headers pkgconf libdrm-dev
```

将源码克隆到 `/root/fastfetch`：

```bash
git clone --depth 1 --branch 2.66.0 \
  https://github.com/fastfetch-cli/fastfetch.git \
  /root/fastfetch
```

如果 GitHub 直连卡住，停止当前命令后，通过局域网代理重试：

```bash
git -c http.proxy=http://192.168.31.233:7890 \
  -c https.proxy=http://192.168.31.233:7890 \
  clone --depth 1 --branch 2.66.0 \
  https://github.com/fastfetch-cli/fastfetch.git \
  /root/fastfetch
```

使用 Unix Makefiles 配置最小功能构建。不要使用 Ninja/Samurai，它在本次 iSH 环境中卡在 CMake ABI 测试；同时关闭 LTO，避免最终链接耗时过长：

```bash
cmake -S /root/fastfetch \
  -B /root/fastfetch/build-ish \
  -G 'Unix Makefiles' \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_INSTALL_PREFIX=/usr/local \
  -DIS_MUSL=ON \
  -DENABLE_LTO=OFF \
  -DSET_TWEAK=OFF \
  -DBUILD_TESTS=OFF \
  -DBUILD_FLASHFETCH=OFF \
  -DENABLE_VULKAN=OFF \
  -DENABLE_WAYLAND=OFF \
  -DENABLE_XCB_RANDR=OFF \
  -DENABLE_XRANDR=OFF \
  -DENABLE_DRM=ON \
  -DENABLE_GIO=OFF \
  -DENABLE_DCONF=OFF \
  -DENABLE_DBUS=OFF \
  -DENABLE_SQLITE3=OFF \
  -DENABLE_RPM=OFF \
  -DENABLE_IMAGEMAGICK7=OFF \
  -DENABLE_IMAGEMAGICK6=OFF \
  -DENABLE_CHAFA=OFF \
  -DENABLE_ZLIB=OFF \
  -DENABLE_EGL=OFF \
  -DENABLE_GLX=OFF \
  -DENABLE_OPENCL=OFF \
  -DENABLE_FREETYPE=OFF \
  -DENABLE_PULSE=OFF \
  -DENABLE_DDCUTIL=OFF \
  -DENABLE_ELF=OFF \
  -DENABLE_EET=OFF \
  -DENABLE_LUA=OFF \
  -DENABLE_QUICKJS=OFF \
  -DENABLE_LIBZFS=OFF
```

编译并安装。双任务并行在本次环境中可以稳定完成：

```bash
cmake --build /root/fastfetch/build-ish --parallel 2
cmake --install /root/fastfetch/build-ish
```

iSH 的默认 PATH 是 `/bin:/usr/bin:/sbin:/usr/sbin`，不包含 `/usr/local/bin`。创建软链接后即可直接运行：

```bash
test -e /usr/bin/fastfetch || \
  ln -s /usr/local/bin/fastfetch /usr/bin/fastfetch

fastfetch --version
fastfetch
```

本次实测版本输出为 `fastfetch 2.66.0 (i386)`，并能识别 `Alpine Linux v3.14 i686` 和 `Linux 4.20.69-ish`。

Koishi 最低需要 Node.js 18，推荐使用仍受维护的 LTS 版本。安装前先查询仓库候选版本：

```bash
apk policy nodejs
```

在本文的 Alpine 3.14.3 + USTC 源环境中，实测只能得到：

```text
nodejs policy:
  14.21.3-r0:
    https://mirrors.ustc.edu.cn/alpine/v3.14/main
```

因此，下面的命令虽然能安装 Node.js 和 npm，但得到的是 Node.js 14，不能运行当前 Koishi：

```bash
apk add nodejs npm
node --version
npm --version
```

不要为了获得 Node.js 18 而在 Alpine 3.14 中混入 `edge`、`latest-stable` 或其他大版本仓库。Node.js 官方与 unofficial-builds 的 Node 22/24 Release 也没有 Linux i686 二进制。本文实测采用独立 Alpine 3.21 x86 chroot，保留 iSH 原系统不动，并从 Alpine 官方包安装 Node.js 22。

### 创建 Alpine 3.21 隔离环境

实际部署位置如下：

```text
iSH 宿主目录：/root/alpine-node22
chroot 内根目录：/
chroot 内 Koishi 项目：/root/koishi-app
iSH 宿主看到的项目：/root/alpine-node22/root/koishi-app
```

#### chroot 与 proot-distro 的区别

`chroot` 是 change root 的缩写。它让进程把宿主中的 `/root/alpine-node22` 当作自己的 `/`，因此同一个项目在宿主中是 `/root/alpine-node22/root/koishi-app`，进入 chroot 后则是 `/root/koishi-app`。

它不是虚拟机或 Docker：内外两套 Alpine 仍共享 iSH 实现的内核接口、x86 模拟、内存、网络和 iPadOS 生命周期，只隔离根文件系统和软件包。本文利用它从 Alpine 3.21 仓库安装 Node.js 22，同时避免把 Alpine 3.14 宿主与新版系统库混装。

它和 Termux 中常见的 `proot-distro` 用途相近，但实现不同。`chroot` 使用内核能力，通常要求 root；PRoot 在用户态拦截并改写路径和系统调用，不要求 root，但通常有额外开销。更换根文件系统并不会更换底层内核，因此 Node.js 仍需要本文后面的 iSH syscall 与 V8 兼容层。

下载 Alpine 3.21.7 x86 minirootfs。直连失败时先设置本文前面使用的局域网代理：

```bash
cd /root

wget -O alpine-minirootfs-3.21.7-x86.tar.gz \
  https://mirrors.ustc.edu.cn/alpine/v3.21/releases/x86/alpine-minirootfs-3.21.7-x86.tar.gz

echo 'b6ca484f1a667990b1276bcc4811ab0617557a13bef5ff03be2e2600ad717477  alpine-minirootfs-3.21.7-x86.tar.gz' \
  | sha256sum -c -
```

只有校验输出 `OK` 才继续解压：

```bash

  -C /root/alpine-node22
cp -L /etc/resolv.conf /root/alpine-node22/etc/resolv.conf
```

将新环境自己的 Alpine 3.21 仓库切换到 USTC，不要修改成 3.14：

```bash
  's|https\?://dl-cdn\.alpinelinux\.org/alpine|https://mirrors.ustc.edu.cn/alpine|g' \

cat /root/alpine-node22/etc/apk/repositories
```


```bash
test -e /root/alpine-node22/dev/null    || mknod -m 666 /root/alpine-node22/dev/null c 1 3
```

安装 Node.js 22、npm 和基础工具：

```bash

chroot /root/alpine-node22 /sbin/apk add \

```

```text

npm 10.9.1
```

这里的 Node.js 22 来自 Alpine 3.21 官方 i686 软件包，不是从 Node.js 源码本地编译。

### 添加 iSH 兼容层

Alpine 的 Node 22 包能显示版本，但直接执行 JavaScript 时，iSH 内核会记录 `missing syscall 425` 并以 `Bad system call` 终止进程。`425` 是 `io_uring_setup`。npm 还会使用 iSH 缺失的 i386 `pwritev`，而 V8 的 TurboFan 在 iSH 中会触发页错误。

下面的兼容层负责这些问题：让 `io_uring_setup` 返回标准的 `ENOSYS` 以触发 libuv 回退；用 `pwrite()` 模拟 `pwritev()`；修复新版 musl 在未修补 iSH 中触发的 `connect EINVAL`；限制 V8 的优化与后台编译；确保 Worker 和显式清空 `execArgv` 的 fork 子进程仍能获得正确参数；在 iSH 无法枚举网卡时让 `os.networkInterfaces()` 返回空对象。Fastfetch 编译章节已经安装了宿主的 `build-base`；如果跳过了该章节，先执行：

```bash
apk add build-base
```

用 nano 创建源码：

```bash
nano /tmp/no_io_uring.c
```

写入以下内容并保存：

```c
#define _GNU_SOURCE

#include <dlfcn.h>
#include <errno.h>
#include <stdarg.h>
#include <stddef.h>
#include <sys/types.h>
#include <sys/uio.h>
#include <unistd.h>

typedef long (*syscall_fn)(long, ...);

ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt, off_t offset)
{
    ssize_t total = 0;

    for (int i = 0; i < iovcnt; ++i) {
        const char *buffer = iov[i].iov_base;
        size_t remaining = iov[i].iov_len;

        while (remaining > 0) {
            ssize_t written = pwrite(fd, buffer, remaining, offset + total);

            if (written < 0) return total > 0 ? total : -1;
            if (written == 0) return total;

            buffer += written;
            remaining -= (size_t) written;
            total += written;
        }
    }

    return total;
}

long syscall(long number, ...)
{
    static syscall_fn real_syscall;
    va_list args;
    long a1, a2, a3, a4, a5, a6;

    if (number == 334 || number == 425) {
        errno = ENOSYS;
        return -1;
    }

    if (real_syscall == NULL) {
        real_syscall = (syscall_fn) dlsym(RTLD_NEXT, "syscall");
        if (real_syscall == NULL) {
            errno = ENOSYS;
            return -1;
        }
    }

    va_start(args, number);
    a1 = va_arg(args, long);
    a2 = va_arg(args, long);
    a3 = va_arg(args, long);
    a4 = va_arg(args, long);
    a5 = va_arg(args, long);
    a6 = va_arg(args, long);
    va_end(args);

    return real_syscall(number, a1, a2, a3, a4, a5, a6);
}
```

编译到 chroot：

```bash
mkdir -p /root/alpine-node22/usr/local/lib
gcc -shared -fPIC -O2 -Wall -Wextra \
  -o /root/alpine-node22/usr/local/lib/libish-node-compat.so \
  /tmp/no_io_uring.c -ldl
```

Alpine 3.21 的 i386 musl 会优先调用新式 `connect` syscall。当前 App Store 版 iSH 在把 Linux `sockaddr` 转为 iOS/BSD `sockaddr` 时没有填写 `sa_len`，会返回 `EINVAL`；musl 只有收到 `ENOSYS` 才会回退到旧式 `socketcall`。因此 `wget` 可能正常，而 Node 22 的 `http`、Undici 或 Puppeteer 仍会出现：

```text
connect EINVAL 127.0.0.1:9222 - Local (undefined:undefined)
```

```c
#include <stdint.h>
#include <sys/socket.h>

#if !defined(__i386__)
#error "This compatibility shim is intended for iSH's i386 userspace."
#endif

#define I386_NR_SOCKETCALL 102
#define SOCKETCALL_CONNECT 3

static long i386_syscall2(long number, long first, long second)
{
    long result;

    __asm__ volatile(
        "pushl %%ebx\n\t"
        "movl %2, %%ebx\n\t"
        "int $0x80\n\t"
        "popl %%ebx"
        : "=a" (result)
        : "0" (number), "r" (first), "c" (second)
        : "memory");

    if ((unsigned long) result >= (unsigned long) -4095) {
        errno = (int) -result;
        return -1;
    }

    return result;
}

int connect(int socket, const struct sockaddr *address, socklen_t address_len)
{
    unsigned long arguments[3] = {
        (unsigned long) socket,
        (unsigned long) address,
        (unsigned long) address_len,
    };

    return (int) i386_syscall2(
        I386_NR_SOCKETCALL,
        SOCKETCALL_CONNECT,
        (long) (uintptr_t) arguments);
}
```

```js
const NativeWorker = workerThreads.Worker
const childProcess = require('node:child_process')
const nativeFork = childProcess.fork
const os = require('node:os')
const nativeNetworkInterfaces = os.networkInterfaces

os.networkInterfaces = function ishNetworkInterfaces() {
  try {
    return nativeNetworkInterfaces()
  } catch (error) {
    if (error?.code !== 'ERR_SYSTEM_ERROR') throw error
    return {}
  }
}

const forkExecArgv = [
  '--no-turbofan',
  '--no-wasm-tier-up',
  '--liftoff-only',
  '--no-concurrent-recompilation',
  '--wasm-num-compilation-tasks=1',
  '--single-threaded',
  '--require',
  '/usr/local/lib/ish-node-bootstrap.cjs',
]

const incompatibleWorkerFlags = new Set([
  '--no-turbofan',
  '--no-wasm-tier-up',
  '--liftoff-only',
  '--no-concurrent-recompilation',
  '--wasm-num-compilation-tasks=1',
  '--single-threaded',
])

class IShWorker extends NativeWorker {
  constructor(filename, options = {}) {
    const execArgv = (options.execArgv ?? process.execArgv)
      .filter((option) => !incompatibleWorkerFlags.has(option))

    super(filename, { ...options, execArgv })
  }
}

workerThreads.Worker = IShWorker

childProcess.fork = function ishFork(modulePath, args, options) {
  if (args && !Array.isArray(args)) {
    options = args
    args = []
  }

  options ??= {}
  return nativeFork(modulePath, args ?? [], {
    ...options,
    execArgv: [...forkExecArgv, ...(options.execArgv ?? [])],
  })
}
```

```bash

```

写入：

```js
const puppeteerModule = require('puppeteer-core')
const { get } = require('node:http')
const { Schema, Service } = require('koishi')

const puppeteer = puppeteerModule.default || puppeteerModule

class PuppeteerRemote extends Service {
  static [Service.provide] = 'puppeteer'

  constructor(ctx, config) {
    super(ctx, 'puppeteer')
    this.config = config
  }

  getWebSocketEndpoint() {
    const versionURL = new URL('/json/version', this.config.browserURL)

    return new Promise((resolve, reject) => {
      const request = get(versionURL, (response) => {
        let body = ''
        response.setEncoding('utf8')
        response.on('data', (chunk) => body += chunk)
        response.on('error', reject)
        response.on('end', () => {
          if (response.statusCode !== 200) {
            reject(new Error(`DevTools endpoint returned HTTP ${response.statusCode}`))
            return
          }

          try {
            const endpoint = JSON.parse(body).webSocketDebuggerUrl
            if (!endpoint) throw new Error('webSocketDebuggerUrl is missing')
            resolve(endpoint)
          } catch (error) {
            reject(error)
          }
        })
      })
      request.setTimeout(this.config.protocolTimeout, () => {
        request.destroy(new Error('DevTools endpoint request timed out'))
      })
      request.on('error', reject)
    })
  }

  async connect() {
    if (this.browser?.connected) return this.browser
    if (this.connecting) return this.connecting

    const connecting = this.getWebSocketEndpoint().then((browserWSEndpoint) => {
      return puppeteer.connect({
        browserWSEndpoint,
        defaultViewport: this.config.defaultViewport,
        protocolTimeout: this.config.protocolTimeout,
      })
    })
    this.connecting = connecting

    try {
      const browser = await connecting
      this.browser = browser
      browser.once('disconnected', () => {
        if (this.browser === browser) this.browser = undefined
      })
      return browser
    } finally {
      if (this.connecting === connecting) this.connecting = undefined
    }
  }

  async start() {
    try {
      const browser = await this.connect()
      this.logger.info('connected to remote browser: %s', await browser.version())
    } catch (error) {
      this.logger.warn('remote browser is unavailable at %s; page() will retry', this.config.browserURL)
      this.logger.warn(error)
    }
  }

  async stop() {
    this.browser?.disconnect()
    this.browser = undefined
  }

  page = async () => {
    return (await this.connect()).newPage()
  }
}

PuppeteerRemote.Config = Schema.object({
  browserURL: Schema.string()
    .description('Chrome DevTools HTTP endpoint.')
    .default('http://127.0.0.1:9222'),
  protocolTimeout: Schema.natural()
    .description('CDP request timeout in milliseconds.')
    .default(60000),
  defaultViewport: Schema.object({
    width: Schema.natural().default(1280),
    height: Schema.natural().default(768),
    deviceScaleFactor: Schema.number().min(0).default(1),
  }),
})

module.exports = PuppeteerRemote
```

这里没有把 `browserURL` 直接传给 `puppeteer.connect()`。Puppeteer 的该模式会用 Node 内置 Undici `fetch()` 请求 `/json/version`，在本机仍会触发 `connect EINVAL`；先使用已验证可用的 `node:http` 取得 `webSocketDebuggerUrl`，再连接 WebSocket，才能稳定工作。

回到 Windows PowerShell，以后台形式建立隧道：

```powershell
$sshArgs = @(
  '-4', '-N', '-T', '-F', 'NUL'
  '-p', '2222'
  '-i', "$env:USERPROFILE\.ssh\id_ed25519"
  '-o', 'IdentitiesOnly=yes'
  '-o', 'BatchMode=yes'
  '-o', 'ExitOnForwardFailure=yes'
  '-o', 'ServerAliveInterval=15'
  '-o', 'ServerAliveCountMax=3'
  '-R', '0.0.0.0:9223:127.0.0.1:9222'
  'root@192.168.31.163'
)

Start-Process \
  -FilePath "$env:WINDIR\System32\OpenSSH\ssh.exe" \
  -ArgumentList $sshArgs \
  -WindowStyle Hidden
```

`-F NUL` 会忽略当前用户 `~/.ssh/config`，避免其中已有的端口转发干扰这条专用隧道。隧道含义是：在 iPad 上监听 `9223`，收到的连接经 SSH 加密转发到 Windows 的 `127.0.0.1:9222`。

## 🔹 iSH 环境的限制

### 判断 iSH 闪退的真正原因

2022 款 iPad Air 5 的官方规格是 Apple M1、8 核 CPU、8 核 GPU 和 8 GB RAM。但 8 GB 是 App、iPadOS 系统进程和内核共享的整机物理内存，并非 iSH 可独占的额度。Apple 还明确说明，单个 App 的内存上限会在生命周期内变化，不必与设备物理内存容量对应。App 切换器显示的是 UIKit 保留的界面快照，“只剩 iSH 一张卡片”并不等于 RAM 中只有 iSH。

Fastfetch 显示的 `6.67 GiB / 7.64 GiB (87%)` 也不是 iSH 自己占了 6.67 GiB。iSH 把宿主的整机总内存和完全空闲页写入 `/proc/meminfo`，同时将 Cached、Swap 等大量字段写成 `0`；Fastfetch 只能用 `total - free` 粗略估算。这个百分比包含 iPadOS、系统进程、缓存和压缩页，不是 iSH 的 RSS，也看不出 iSH 距离 Jetsam 上限还有多少。

除 Jetsam 外，本次 Node 负载还有一个直接对应的崩溃疑点：iSH 当前存在未合并的 PR #2706，其中描述了 `mem_ptr()` 写时复制路径的并发竞态。PR 作者在 iOS Simulator（iPhone 16 Pro、iOS 18.4）中使用 Node.js 20 和 10 个以上 Worker，可将未修补 iSH 复现到直接退回主屏，崩溃签名为 `_platform_memmove` → `mem_ptr` → `EXC_BAD_ACCESS`。本项目的 Node 22、Koishi 启动器与工作进程也会产生多条线程，因此该缺陷是有现实依据的候选。但 #2706 仍是未合并的第三方修复，而且它的复现设备不是本机实体 iPad；必须看本机 `.ips` 签名才能定性。App Store 当前稳定版 iSH 仍为 `1.3.2`（2023-05-21），当然不包含 2026 年仍未合并的修复。

出现闪退后，到 iPad 的“设置 → 隐私与安全性 → 分析与改进 → 分析数据”，查找同一时间附近的 `iSH_*.ips` / `iSH-*.ips` 和 `JetsamEvent_*.ips` / `JetsamEvent-*.ips`：

- `JetsamEvent` 中 iSH 的 `reason` 为 `per-process-limit`：单进程超过动态内存上限。
- `reason` 为 `vm-pageshortage`：整机内存压力；`vnode-limit` 或 `fc-thrashing` 则可能与 npm 的大量小文件或文件缓存有关。
- `iSH_*.ips` 中的 `EXC_BAD_ACCESS`、`_platform_memmove` 和 `mem_ptr` 串联出现：高度指向 #2706；`SIGABRT` 或其他触发线程则需按栈追踪单独分析。
- `Termination Reason` 中的 `0x8badf00d` 是 watchdog 因长时间无响应终止 App；`EXC_RESOURCE` 中的 MEMORY 或 CPU 也能提供方向。
- iSH 内的 `dmesg` 只能看到模拟 Linux 客体的错误，不能代替 iPadOS 的 `.ips` 分析日志。

如果只是切后台后 SSH 停顿，但 iSH 界面没有消失，更像 iPadOS suspend 或网络断开。如果 iSH 整个退回主屏，重开后 Linux 进程也全部丢失，才是 host App 被 Jetsam 或 iSH 原生崩溃。在拿到本机 `.ips` 前，#2706 并发竞态与 Jetsam 都是有依据的候选，现阶段无法在二者之间可靠排序。

降低风险的实用做法是：保持 iSH 前台和屏幕常亮；安装依赖前停止 Koishi；继续使用本文的 V8 单线程参数、`UV_THREADPOOL_SIZE=1`、`256 MiB` npm 堆限制和 `maxsockets=2`；直接运行 Koishi CLI 而不保留 npm 进程；禁用当前不兼容的插件市场；一次只增加一个或一小组插件；避免同时安装完整开发依赖、适配器、Puppeteer 和原生模块。这些只是降低触发概率，不是对 iSH 原生竞态的根治。

- iPadOS 会暂停或终止后台应用，SSH 和 Koishi 都无法保证长期在线。
- iSH 的 x86 用户态模拟速度明显低于原生运行，安装大量 npm 依赖时尤其明显。
- 部分 Node.js 原生模块不提供 32 位 x86 或 musl 构建，源码编译也不一定成功。
- 完整模板一次解析 700 多个包；本次 npm 解包到约 290 MB 时 iSH 整个应用闪退，但不应在没有 `.ips` 的情况下将原因写死为内存不足。
- iPadOS 终止或 iSH 原生崩溃都会让 SSH、`sshd` 和 Koishi 一起消失；重开 iSH 后需手动重启这些服务。
- iSH 适合学习、验证和临时调试，不适合作为稳定的生产环境。

完成最小验证后，可以在 Koishi 控制台中安装和配置插件；若需要机器人长期在线，建议把验证通过的项目迁移到原生 Linux 服务器或其他受支持的 Node.js 主机。
